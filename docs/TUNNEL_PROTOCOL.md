# fmcp-tunnel/1 Protocol

End-to-end protection for the WebSocket tunnel between FluidMCP (client) and GPT Engine (server).
It runs inside `wss://`, after the server has checked the tunnel token, and gives:

- mutual authentication with long-term Ed25519 identity keys, so a stolen token alone is useless;
- per-connection session keys from an ephemeral X25519 exchange (forward secrecy);
- AES-256-GCM encryption and authentication of every message, separate keys per direction;
- strict sequence numbers (no replay, reordering or dropped messages);
- hourly re-keying inside the connection.

Reference implementation: [fluidmcp/cli/tunnel/protocol.py](../fluidmcp/cli/tunnel/protocol.py).
GPT Engine uses a byte-identical copy. Both sides run [tests/tunnel_test_vectors.json](../tests/tunnel_test_vectors.json)
(generated by [scripts/gen_tunnel_vectors.py](../scripts/gen_tunnel_vectors.py)); if an implementation disagrees with the
vectors, the implementation is wrong.

Primitives (all from `cryptography`): X25519, Ed25519, HKDF-SHA256, AES-256-GCM, SHA-256.

## Conventions

- Integers are big-endian unsigned: `u8`, `u32`, `u64`. `‖` is concatenation.
- `lp(x) = u8(len(x)) ‖ x`.
- All protocol messages are WebSocket **binary** frames. A text frame is a protocol error.
- Public keys are 32 raw bytes; in configuration they are standard base64 with padding.

| Constant | Value |
|---|---|
| `VERSION` | `0x01` |
| `CTX_TRANSCRIPT` | `"fmcp-tunnel/1 transcript"` |
| `CTX_SIG_SERVER` | `"fmcp-tunnel/1 server signature"` |
| `CTX_SIG_CLIENT` | `"fmcp-tunnel/1 client signature"` |
| `INFO_INIT` | `"fmcp-tunnel/1 session keys"` |
| `INFO_REKEY` | `"fmcp-tunnel/1 rekey keys"` |
| `CTX_REKEY_TH` | `"fmcp-tunnel/1 rekey transcript"` |
| `DIR_C2S` / `DIR_S2C` | `0x01` / `0x02` |
| Max frame | 10 MiB (10 485 760 bytes) |
| Clock skew allowed | ±60 s |
| Handshake timeout | 10 s |
| Re-key | every 3600 s or 100 000 records (client starts it) |
| Re-key ack timeout | 30 s |
| Old key grace | 30 s |
| Server max key age | 7200 s |
| Connector ID | `^[A-Za-z0-9._:-]{1,64}$` |

## Handshake

| Message | Layout | Size |
|---|---|---|
| `CLIENT_HELLO` | `0x01 ‖ 0x01 ‖ ts u64 ‖ eph_pub_C 32 ‖ nonce_C 32 ‖ client_id_pub 32 ‖ cid_len u8 ‖ connector_id` | 107 + cid_len |
| `SERVER_HELLO` | `0x02 ‖ 0x01 ‖ ts u64 ‖ eph_pub_S 32 ‖ nonce_S 32 ‖ server_id_pub 32 ‖ sig_S 64` | 170 |
| `CLIENT_FINISH` | `0x03 ‖ 0x01 ‖ sig_C 64` | 66 |

`ts` is Unix seconds. `client_id_pub` / `server_id_pub` name which identity key is in use, so each side can allow
up to two keys during rotation.

```
th_S     = SHA256(lp(CTX_TRANSCRIPT) ‖ CH ‖ SH[0:106])
sig_S    = Ed25519_sign(server_key, lp(CTX_SIG_SERVER) ‖ th_S)
th_C     = SHA256(lp(CTX_TRANSCRIPT) ‖ CH ‖ SH ‖ CF[0:2])
sig_C    = Ed25519_sign(client_key, lp(CTX_SIG_CLIENT) ‖ th_C)
th_final = SHA256(lp(CTX_TRANSCRIPT) ‖ CH ‖ SH ‖ CF)
```

**Server, on CLIENT_HELLO:** check type, version and exact length; connector ID matches the pattern and equals the
connector authenticated by the token (constant-time); `|now − ts| ≤ 60`; `client_id_pub` is in the connector's allowed
keys (constant-time over the whole set). Then generate `eph_S` and `nonce_S`, compute the X25519 shared secret (fail on
an error or an all-zero result) and send SERVER_HELLO.

**Client, on SERVER_HELLO:** check type, version and length; `server_id_pub` is one of the pinned keys; verify `sig_S`;
`|now − ts| ≤ 60`; `eph_pub_S ≠ eph_pub_C` and `nonce_S ≠ nonce_C`; compute the shared secret; send CLIENT_FINISH.

**Server, on CLIENT_FINISH:** check type, version and length; verify `sig_C` with `client_id_pub` from CLIENT_HELLO.

The whole handshake must finish within 10 s. Nothing else is accepted before it completes. A replayed CLIENT_HELLO only
produces a fresh SERVER_HELLO; a replayed CLIENT_FINISH fails because it signs the server's fresh values.

## Session keys

```
k_c2s ‖ k_s2c ‖ ck = HKDF-SHA256(ikm = shared, salt = th_final, info = lp(INFO_INIT) ‖ u32(1), length = 96)
```

`ck` is a chaining key used only to derive the next keys. This is key number 1.

## Records

Every message after the handshake:

```
frame = u32(key_no) ‖ u64(seq) ‖ AES-256-GCM(key, nonce, inner, aad)     (ciphertext includes the 16-byte tag)
nonce = 0x00000000 ‖ u64(seq)
aad   = u8(sender_dir) ‖ u32(key_no) ‖ u64(seq)
inner = u8(type) ‖ body
```

| Inner type | Name | Direction | Body |
|---|---|---|---|
| `0x00` | DATA | both | application bytes (UTF-8 JSON) |
| `0x01` | REKEY | client → server | `u32(new_key_no) ‖ eph_pub_C' 32` |
| `0x02` | REKEY_ACK | server → client | `u32(new_key_no) ‖ eph_pub_S' 32` |

- The client encrypts with `k_c2s`, the server with `k_s2c`.
- `seq` counts per direction from 0, increases by exactly 1, and is **not** reset at re-key. A receiver accepts only
  `seq == expected`.
- Frame length must be between 29 bytes and 10 MiB.
- Any failure (bad length, sequence, key number, tag, inner type, direction) closes the connection.

## Re-keying

1. The client sends REKEY with `new_key_no = key_no + 1` and a fresh ephemeral key, under the current key. It may keep
   sending DATA under the current key until the ack arrives.
2. The server checks the REKEY arrived under its current key with `new_key_no = key_no + 1`, generates its own ephemeral
   key, derives the new keys, sends REKEY_ACK **under the current key**, then switches its sending key. It keeps
   accepting client records under the old key until the first record under the new key or for 30 s, whichever is first.
3. The client derives the new keys on REKEY_ACK and switches both directions.

```
rth = SHA256(lp(CTX_REKEY_TH) ‖ th_final ‖ u32(n) ‖ eph_pub_C' ‖ eph_pub_S')
k_c2s ‖ k_s2c ‖ ck_n = HKDF-SHA256(ikm = X25519(eph_C', eph_S'), salt = ck_(n-1), info = lp(INFO_REKEY) ‖ u32(n) ‖ rth, length = 96)
```

Timers (callers run `check_timers()` every few seconds):

- Client: REKEY without an ack for 30 s → close.
- Server: no re-key for 2 hours → close. The client reconnects with a fresh handshake.

## Errors

Every failure raises `ProtocolError`. The caller closes the WebSocket with code **1008** and an empty reason. The
internal `code` is logged locally and never sent to the peer.

## Using the module

```python
# client (FluidMCP)
handshake = ClientHandshake(identity_key, server_public_keys, connector_id)
await ws.send(handshake.start())
client_finish, channel = handshake.receive_server_hello(await ws.recv())
await ws.send(client_finish)

# server (GPT Engine)
handshake = ServerHandshake(identity_key, client_public_keys, connector_id)
await ws.send(handshake.receive_client_hello(await ws.recv()))
channel = handshake.receive_client_finish(await ws.recv())

# both
frame = channel.encrypt(data)            # bytes -> DATA record
result = channel.decrypt(frame)          # bytes, or ControlMessage for re-key traffic
channel.check_timers()                   # every few seconds
if channel.needs_rekey():                # client only
    await ws.send(channel.start_rekey())
```

`SecureChannel` is not task-safe. Run each `encrypt`/`decrypt`/`start_rekey` together with the send of its result
under one `asyncio.Lock` per connection, and send a `ControlMessage.reply` immediately under the same lock. If a send
fails, close the connection; never encrypt the same data again.
